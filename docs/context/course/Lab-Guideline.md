# **AM/ME/CE 295 — Lab Guideline: Biweekly Demos & Reports**

The 4 weekly lab hours are for building your own final research project — not the graded weekly labs. Every two weeks you turn in a short report and demo of that project's progress. This guideline sets concrete expectations for each of the five Lab Reports.

## **Assessment**

| Technical depth | Reproducibility | Results and analysis | Writing | Participation |
| :---: | :---: | :---: | :---: | :---: |
| **30%** | **20%** | **25%** | **15%** | **10%** |

- For participation, we will check on the commits activity for the github repo that you are working on. 

## **What Every Lab Report Includes**

> * **Repository link** — your GitHub repo, current commits, up-to-date README  
> * **Progress report** from your running log: done / remaining / bottlenecks  
> * **Demo of the current state** — a small working part is fine early on  
> * **Next steps** for the coming two weeks

## **Lab Report 1 — Weeks 1–2 (due Fri, Oct 16\)**

Due date confirmed by Andrew, 2026-10-16: Sun Oct 18, 11:59 pm.

**Goal:** Lay the foundation for your project before it's formally proposed. At this point you don't have a locked-in topic or team yet, so the goal isn't a working demo — it's making sure you understand the problem space you're heading into and that your tooling is ready to build in. Read enough of the relevant literature to know what's already been tried and where a gap might be. Get your repository, environment, and API access working now so early setup issues don't cost you time later. Treat this report as evidence that you've started, not that you've built something yet.  
**Potential Deliverables:**

> * Related-work note: 2-3 papers/approaches relevant to your intended project, with a short synthesis  
> * Repo and environment set up; running log started  
> * Draft project proposal, including the problem statement or goal 

## **Lab Report 2 — Weeks 3–4 (due Fri, Oct 30\)**

**Goal:** Lock in your project direction. This is the point where your idea needs to go from a loose interest to a defined research question with a specific domain-specific tool you'll integrate. The proposal you submit should reflect what you've learned since Lab Report 1's related-work note, including any pivots. If you're working in a team, this is also when team composition needs to be finalized with the TA. Treat this report as your commitment point — what you propose here is what Lab Reports 3-5 will track progress against.  
**Potential Deliverables:**

> * The 1-page project proposal (this *is* the report for this period)  
> * Updated related-work note reflecting any changes  
> * Confirmation that the repo and log are actively maintained

## **Lab Report 3 — Weeks 5–6 (due Fri, Nov 13\)**

**Goal:** Show first working progress on your project. By now the project is defined, and you should have moved from planning into building — even a small, rough piece counts. This is the first cycle where a genuine demo is expected, so pick the smallest slice of your system that can actually run end to end. It's fine if it only covers one component, uses a toy input, or falls short of your eventual design — the point is to prove the approach is workable before you invest further. Use this report to surface early technical risks while there's still time to change course.  
**Potential Deliverables:**

> * A small but real working piece of the system (e.g. data pipeline, baseline model)  
> * Progress report per the standard format above  
> * Next steps toward integration

## **Lab Report 4 — Weeks 7–8 (due Mon, Nov 23\)**

**Goal:** Demonstrate an integrated, end-to-end run. The individual pieces you built in the previous cycle should now work together as a single pipeline or agent workflow on your own problem, not as isolated components. This is also the point to start being honest about where the system breaks — what inputs it can't handle, where it stalls, or where results look plausible but aren't reliable. Naming those failure modes now sets up a focused reliability audit later rather than a last-minute scramble. A demo that clearly shows both what works and what doesn't is worth more here than one that only shows a happy path.  
**Potential Deliverables:**

> * Demo of your system producing output on your own problem  
> * Honest statement of current failure modes
