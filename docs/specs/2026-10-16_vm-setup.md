# Spec: new VM setup — Agent View, task board, interruption safety, literature reviewers

From: planning account. Date: 2026-10-16. Status: open. Decisions by Andrew on 2026-10-16. The VM was wiped at 15:00 and rebuilt with local admin. Backup is in the VM backup folder on the lab server (location in private/).

Note (build account): locations outside the repo are named by role here, per CLAUDE.md. The role-to-path key is in `private/paths.md`.

## Decisions
- Live sessions are run and watched in Claude Code Agent View (`claude agents`). Claude Code v2.1.139 or later
- Agent View worktrees replace the old sibling-folder worktree layout. Worktrees live under `.claude/worktrees/` (gitignored). Branch names stay `wip/<name>`, `heldout/<name>`
- The task board in the repo is the source of truth for who is doing what. Agent View shows live state only and does not survive a wipe
- The VM may stop or time out at an unknown interval. Every task must resume from disk after an interruption
- Literature reviewers are a course-project component: development-time sanity checks, not part of the measurement pipeline. Five papers:
  - Chavarria-Krauser et al. 2008
  - Bastien et al. 2016 (KymoRod)
  - Henry, Miller & Spalding 2023 (PatchTrack), IJMS 24:16475, code github.com/phytoMorph/phytoMorph_kinematics
  - Silk 1978
  - Krupar 2026
- Full Paper2Agent build (paper and code as an MCP server) only for KymoRod and PatchTrack. The other three get a pitfall list and a reviewer
- Reviewers are read-only. They report findings; they change nothing
- A reviewer finding that would change a frozen item goes to Andrew and a new freeze version. Freeze v2 scoring is not touched by this spec
- Paper PDFs are not committed. Pitfall lists paraphrase and cite page, figure or equation

## Limits
- Shared-machine limits as before. One sweep at a time on the lab server
- Check df before writing more than 5 GB on the VM
- Nothing from the research lane goes to the public repo
- Reviewer runs in this spec: at most 30. Paper2Agent builds: at most 2, each stopped after 2 h

### 2. Task board
- `tasks/` in the course repo. One file per task: `tasks/<id>-<name>.md`
- Front matter fields: id, title, lane (course), owner (session name or Andrew), state, branch, created, last_update, blocker, done_marker
- States: queued, working, needs-input, review, done, blocked, interrupted
- Each session updates only its own task file, on its own branch, at start, at each commit, and at stop
- Research-lane tasks use the same format in the research task folder, outside every git repo
- `scripts/board.py`: reads both folders and prints one table (id, lane, owner, state, branch, last_update, blocker). `--html` writes a local page outside the repo. Never committed with research-lane content
- A task with state working and last_update older than 30 min is shown as stale
- Tests: board reads a sample of each state; stale rule; research rows never appear in a tracked file
- Move the open items from the 2026-10-12 specs into task files

### 3. Interruption safety
- Heartbeat: a scheduled job every 5 min appends the date and uptime to the VM health log. Gaps show when the VM stopped. Report the first gap seen to Andrew
- Resume rules, added to CLAUDE.md:
  - State lives on disk and in git, not in a session
  - Commit and push after every unit of work
  - Every task writes a done marker; a restarted task skips finished parts
  - Sweeps write each run to the cache as it finishes; a restarted sweep skips cached runs
  - On start, a session reads its task file first
  - On restart, the coordinator sets working tasks with no live session to interrupted and re-dispatches them
- Nightly backup: `scripts/ops/backup_vm.sh`, run by the scheduler at 02:10. Same layout as the 2026-10-16 backup, to a dated folder in the VM backup folder on the lab server. Host and path read from `private/backup.conf`, never written in a tracked file. Keep the last 7 nightly copies; delete older ones only inside the VM backup folder and only those the script made
- Test the backup once by hand and verify SHA256SUMS on the server
- Do not try to prevent the timeout (no fake activity, no keep-alive). Andrew asks IT for the policy

### 4. Literature reviewers, stage A: pitfall lists
- Papers from Andrew's Papers folder into `private/papers/`. Not tracked
- One file per paper: `docs/lit/pitfalls/<paper>.md`. Each entry:
  - pitfall, in our words
  - source: page, figure or equation
  - what to check in our work: file or result
  - codable: yes (deterministic test) or no (reviewer)
- Include internal inconsistencies in the paper as "do not inherit" entries. For Henry 2023: resolution given as 1500 px/mm (Fig. 1) and 1450 px/mm (methods); peak REGR about 45 %/h (Fig. 2G), 23.7 %/h (abstract), about 29 %/h (Figs. 3–4); the 8.6 %/h value cites Fig. 4A, which plots growth rate
- Starting points for Henry 2023: frame interval against patch motion through the zone; patch rotation in bending roots; logistic fit forcing a sigmoid shape; 20 % zone threshold called arbitrary by the authors
- Stop after the five lists. Andrew checks each list before stage B

### 5. Stage B: codable pitfalls become tests
- Each entry marked codable gets a test in `tests/lit/`, named after the paper and entry
- A test that fails on current main: report it. Do not fix in this spec. If it touches a frozen item, it goes to Andrew

### 6. Stage C: reviewer agents
- One Claude Code subagent per paper: `.claude/agents/lit-<paper>.md`. Tools: Read, Grep, Glob only
- Input: its pitfall list, the paper from `private/papers/`, and the diff or folder under review
- Output: `docs/reviews/<date>_<paper>.md`. Each finding: pitfall entry, paper location, our file and line or result, evidence, severity (would change a reported number / would not)
- Every finding must cite both the paper location and our location. A finding without both is dropped
- Andrew marks each finding accepted or rejected in the same file. Keep the record
- The coordinator runs all five before a freeze and on merges to main. Not on every commit

### 7. Stage D: Paper2Agent for KymoRod and PatchTrack
- First check each repo: language, licence, whether it runs on the VM
- MATLAB with no licence on the VM: stop and tell Andrew
- If it runs: build the MCP server per Paper2Agent, outside the course repo. Record the Paper2Agent commit
- Validate each tool on one fixed root and one bending root, same frames as our tracker
- The reviewer for that paper may call its tools. Add this to its agent file only after validation passes

### 8. Reviewer evaluation
- A separate session, which has not seen the reviewer files, writes planted pitfalls on branch `eval/planted-pitfalls`: at least 2 per paper, each a small change to code or config that repeats a listed pitfall. Recorded in `docs/proposals/<date>_planted-pitfalls.md` on that branch only
- Reviewers run on the planted branch and on clean main
- Report per paper: planted pitfalls caught, false findings on clean main, findings that cite the wrong location
- No change to a pitfall list or reviewer prompt after seeing these results without a new planted set
