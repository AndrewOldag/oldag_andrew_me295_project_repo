## 3. Metrics, computed in code
New `measure/metrics.py`, tests in `tests/test_metrics.py` (hand-worked cases, including all-decline and all-accept). Inputs: one record per run (method, rod, class, repeat, status, outcome category). No metric is computed by hand.

Outcome category per run, as in v2 (`measure/score.py`): `good_report`, `false_accept`, `correct_decline`, `unnecessary_decline`, `not_reported` (step limit or error). One addition: a `good_report` on a `decline` rod is `accept_on_decline`, counted neither correct nor false accept (v2 rule, now a named category)

| Metric | Definition |
| :-- | :-- |
| Accuracy per class | correct runs / runs in the class. Correct: `good_report` on accept_clean and accept_repaired; `correct_decline` on decline |
| Balanced accuracy | mean of the three class accuracies. Primary single number |
| Overall accuracy | correct runs / all runs. Reported, not primary |
| False-accept rate | `false_accept` / runs with status accept. Also given as a count over all runs |
| Coverage | runs with status accept / all runs |
| Abstention precision | `correct_decline` / runs with status decline. Undefined (shown `-`) with no declines |
| Abstention recall | `correct_decline` / runs on decline rods |
| Unnecessary-decline rate | `unnecessary_decline` / runs on accept_clean and accept_repaired rods, per class |
| not_reported | count per class. Counted neither as decline nor as accept in precision, recall and coverage |
| Fault named correct | terminal fault name against the names counted correct, on fault rods |

- An accept_clean run that keeps a remedy and reports a good field counts as correct; the remedies kept on accept_clean rods are reported per method (open item 2)
- References: all-decline and all-accept, computed from the labels and the unremedied runs, in the same table

Repeated-run agreement:
- LLM methods (diagnostician, single agent): 3 repeats per rod, same 48 rods, same seeds, same tracker cache. 144 runs per method
- Deterministic methods (script, remedy tree): 1 run per rod; a second run from the cache checks they are identical (agreement 1 by construction; a mismatch is a bug)
- Primary statistic: unanimity rate = rods on which all 3 repeats give the same outcome category / 48. Per class and overall
- Secondary: Fleiss' kappa over the six outcome categories (the five of v2 and `accept_on_decline`), 48 rods x 3 repeats. Kappa is reported with the category counts, since it is low when one category dominates
- Accuracy and the other metrics: mean over the 3 repeats, with the range (min-max) over repeats

## 6. kinematics-1: correct the width-free ratio for curvature
Choice: correct it. Do not drop the remedy for curved rods.

Why:
- The width change breaks plane sections only through the curvature term (residual 2 kappa dh/dt, `measure/rod.py`). On a straight rod the remedy is never needed. Dropping it for curved rods drops it for every rod where it applies, makes `width_change` not repairable, and moves 3 rods from accept_repaired to decline
- The correction uses quantities the record already has: midline curvature `kappa`, flank spacing (2h) and its rate `flank_spacing_rate` (P4). No new tracker run

Formula, from the flank relations in `measure/rod.py` (p, m: window-mean flank strain rates; D = p - m; S = p + m; g = d ln(spacing)/dt):
- Old: ratio = D / S. With dh/dt != 0 it keeps the kappa dh/dt term
- New: ratio = (D (1 - kappa^2 h^2) + 2 kappa h g) / (S - kappa h D). This equals -h (Dkappa/Dt) / REGR exactly on the field-level rod, with or without a width change. With g = 0 and small kappa h it reduces to D / S
- Tests: field-level `width_change` (zero curvature rate) gives ratio under 1e-3 in magnitude at every grid point where the old one gave -0.035 to -0.435; `growth_zone` gives 0; field-level bent rods give the true -h (Dkappa/Dt) / REGR to 1e-3
- Scoring unchanged: under the width-free ratio the flank term is skipped (`measure/score.py`). The ratio error against truth is recorded per run, not scored
- Remedy name, list position and the info text the agent sees stay. Only the computation changes, before the v3 tag
